# Design — add-core-definition-schemas

## Context

`add-content-package-loader` (1.1) is archived: `@aesfw/content` resolves manifests, parses YAML strictly, and returns parsed files plus diagnostics. TDS-20.4 fixes the published-schema requirement, CONT-4 the ID rules, and CONT-6 the definition shapes. This document records only the choices those documents leave open.

## Goals / Non-Goals

**Goals:** TypeBox schemas for the M1 definition set; stable-ID validation; raw-document schema validation producing grouped raw definitions and diagnostics; the collection catalogue that maps document keys to core definition types; published JSON Schema files.

**Non-Goals:** includes and merge operations (1.3); handle assignment, reference resolution, normalization, checksum, and the compiled `Registry` (1.4); condition/curve compilation (1.6); graph and economic validation (10.1–10.3); the schemas of later rows (balance resources 4.1, placement 3.3, slots/areas 3.5, connections/world 6.1, regions 8.1, services/coverage 7.6, transitions/bands/unlocks/exchanges/deficit/modules 7.3, 7.2, 7.5, 9.1, 4.3, 13.1).

## Decisions

### D1 — Module layout

`packages/content/src/schemas/` holds `common.ts` (shared fragments), `resource.ts`, `location.ts`, `recipe.ts`, `entity.ts`, `population.ts`, `need.ts`, `ids.ts`, `collections.ts` (catalogue and schemas), `validate.ts`, `export.ts`, and `index.ts`. The published JSON Schema files live in `packages/content/schemas/`, generated by `packages/content/scripts/export-schemas.mjs`.

### D2 — Only the M1 definition set is schematised; later rows extend it

Each schema is `additionalProperties: false`, so an unknown field is a `schema_invalid` error and content cannot smuggle in later-row behavior. Later rows add fields or union members additively. `resource_source.policy` accepts only `infinite_rate` here; `need.demand` accepts only `resource_consumption` and `resource_availability`; `location_template` omits `region`, `source_slots`, `internal_logistics`, `knowledge`, and `establishment`; `entity.components` omits placement, construction, capability, connectivity, maintenance, and lifecycle. A package that uses a later-row field is rejected in strict mode, which is the intended M1 behavior.

### D3 — Numeric bounds are expressed in the schema

Quantities, rates, durations, and windows are integers with explicit `minimum`/`maximum` (`scale ≥ 1`, `duration_ticks ≥ 1`, `target_ratio` in `[0, 1000]`, `capacity ≥ 1`, `process_slots ≥ 1`). This keeps invalid content out before any simulation runs and gives the CLI precise paths.

### D4 — Stable IDs are validated separately from the schema

The schema only requires a non-empty string `id`; `isValidDefinitionId` enforces CONT-4 (`/^[a-z0-9_]+(?:\.[a-z0-9_]+)+$/`). Keeping the rule in one exported predicate lets the registry (1.4) and later validators reuse it, and produces the dedicated `invalid_id` diagnostic rather than a generic schema error.

### D5 — Validation groups raw definitions and composes diagnostic paths

`validateSchemas(files, options)` walks each parsed file's top-level keys in document order. It maps a key to a collection through the catalogue, rejects a non-array value with `invalid_definition_document`, and validates each item with `Value.Check`/`Value.Errors`. A schema error's path is `/<collection>/<index><relative-path>`; an ID error's path is `/<collection>/<index>/id`. Valid items are collected into per-collection buckets, and the result object is built by iterating the catalogue's canonical order, so collection order never depends on document key order. The function returns diagnostics and never throws.

### D6 — The catalogue is the single source of collection order and types

`DEFINITION_COLLECTIONS` maps each M1 document key to a core `DefinitionType` in canonical order; `COLLECTION_ORDER` is its key tuple and `DEFINITION_SCHEMAS` its schema map. Roadmap 1.4 iterates `COLLECTION_ORDER` to assign handles, so this ordering is the handle space's definition.

### D7 — JSON Schema is a generated, committed build artifact

`exportJsonSchemas()` returns each collection schema keyed by `<collection>.json`. `packages/content/scripts/export-schemas.mjs` imports the built `dist/schemas/export.js`, writes the files, and is exposed as `pnpm --filter @aesfw/content export:schemas`. A test compares the committed files (parsed) with `exportJsonSchemas()` so drift fails `pnpm verify`. The TypeBox objects are already JSON Schema; no transformation is applied.

### D8 — Dependencies and versioned artifacts

No new runtime dependency is added; `@sinclair/typebox` was already a `@aesfw/content` dependency. No versioned algorithm, save format, protocol version, or golden hash changes.

## Risks / Trade-offs

- [The M1 schema subset rejects later-row fields] → intended; later rows extend the schemas in the same change that implements their behavior, and no M1 fixture uses them.
- [`Type.Unknown()` for `spatial_parameters`] → spatial parameters are policy-specific (abstract capacity now, grid later); a permissive record avoids pre-empting `add-grid-spatial-policy` (3.1) while keeping the outer shape strict.
- [Generated JSON Schema files can drift] → the export test fails `pnpm verify` on drift, so the artifact cannot silently diverge.
- [Path composition differs from the loader's] → paths are diagnostic-only and documented in D5; they are stable for a given schema.

## Migration Plan

Additive source, schema, and test files plus generated artifacts. No state, save, protocol, or golden artifacts exist. Rollback is reverting the change.
