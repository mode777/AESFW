# Abstract Economic Simulation Framework
## Core Game Framework GDD

**Version:** 1.1  
**Status:** Implementation baseline  
**Purpose:** Define the invariant game mechanics and the core design ideas of a configurable, abstract, theme-free economic settlement framework.  
**Lineage:** Economic city-building games very strongly inspired by the Anno series. The original abstract game concept (working title TIER) is fully absorbed into this specification; see Appendix A and Appendix B.

---

## 1. Purpose and Scope

This document defines a game framework, not a configured game. It specifies the design ideas every configuration must preserve and the mechanics that must remain invariant across all configurations.

The framework is the distilled formula of the economic city-building genre as exemplified by the Anno series, with everything removed that is not load-bearing: no setting, era, fiction, military, diplomacy, or narrative. It consists of exactly five coupled layers plus the progression that escalates them:

1. Stratified (tiered) aggregate population
2. Categorized needs
3. Cycle-based resource transformation chains
4. Spatially distributed, scarce resource availability
5. Logistics between isolated inventories
6. Condition-driven progression that raises demand along the five layers

All concrete content is external configuration, including resource names, population tiers, buildings, recipes, locations, transport types, exchanges, balancing, terminology, and presentation.

The framework has no intrinsic assumptions about history, geography, narrative, cultures, factions, competitors, combat, missions, disasters, decoration, characters, or technology trees. Tension is produced exclusively by economic scarcity, never by conflict.

A valid simulation must operate headlessly with one player, no opponents, no random incidents, and no presentation layer. Other players, scenario objectives, and disruptions are optional modules (Section 21) that support none of the core systems.

## 2. Core Design Statement

The framework models aggregate population groups that create configurable demand and capabilities. Configurable entities transform resources through recipes. Independently inventoried locations constrain availability. Configurable transport processes connect those locations. Condition-driven transitions create progression.

The five layers form a **closed loop**. Population is both the source of demand and the source of the workforce and income that production requires:

```text
             ┌──────────── provides workforce capabilities + income ────────────┐
             │                                                                    ↓
Stratified population ──demands──▶ Categorized needs ──forces──▶ Cycle-based production chains
             ▲                                                                    │
             │                                                                 requires
          supplies                                                                ↓
             │                                                Spatially distributed, scarce sources
             │                                                                    │
             └────────── Logistics across separate inventories ◀────forces────────┘

Progression: satisfied population advances to higher tiers → higher tiers demand
more complex chains, more distant sources, and more logistics → the loop escalates.
```

The player continuously solves **one single problem in four currencies**:

| Currency | Framework mechanism |
| --- | --- |
| **Throughput** | Recipe rates, internal-logistics throughput, transport capacity |
| **Space** | Finite location capacity, placement footprints, finite source slots |
| **Workforce** | Location-scoped capabilities generated by specific population tiers |
| **Balance** | Owner-scoped continuous income versus continuous maintenance |

Every complete-game configuration (Section 23.4) must keep all four currencies in play. A configuration in which one currency is never binding has removed a decision dimension. Reduced configurations (Sections 23.1–23.3) are valid only as mechanical and test fixtures.

## 3. Core Design Ideas

These ideas are the reason the mechanics in later sections exist. Mechanics may be parameterized freely; these ideas must survive every configuration. Section 25 turns them into acceptance criteria.

### 3.1 Five coupled layers and the decoration test

Each of the five layers is necessary: remove one and the loop collapses. Removing population removes demand; removing categorized needs removes the reason to diversify; removing transformation chains removes planning; removing spatial scarcity removes expansion; removing isolated inventories removes logistics.

**Decoration test:** a proposed system that does not feed back into at least one of the five layers is decoration and does not belong in the framework core. It may at most be an optional module (Section 21).

### 3.2 Scarcity replaces conflict

There is no military, opponent, or random threat in the core. All tension comes from independent, configurable scarcities, each of which the framework must be able to express:

| Scarcity | Framework mechanism | Pressure created |
| --- | --- | --- |
| Finite space | Location capacity and footprints | Every location forces a choice between residences and production. |
| Finite source slots | Slot-limited sources | Forces expansion and therefore logistics. |
| Disjoint source distribution | Region membership and location property vectors | Makes self-sufficiency of any single location or region impossible. |
| Exact workforce-class binding | Exact capability matching | Turns advancement into a trade-off instead of an automatic process. |
| Throughput limit | Internal-logistics throughput capacity | Punishes over-densification. |
| Maintenance while idle | Utilization-independent continuous costs | Punishes unbalanced chains. |
| Asymmetric decline | Decline transitions without refund and with population loss | Punishes growth that outruns supply. |

A configuration intended as a complete game should activate all seven. Content validation reports which scarcities are inactive (Content Configuration Specification, economic diagnostics).

### 3.3 Interdependence by distribution rule

Long-distance logistics exists for exactly one reason: **no location, and no region, can supply every raw resource.** This is expressed as a pure distribution rule over location property vectors and region membership, never as geography, culture, or fiction. Higher tiers should require inputs that originate in more than one region, so that advancement necessarily depends on logistics.

### 3.4 Lower tiers are structurally indispensable (pyramid rule)

Producers require a **specific** capability, not "a capability of at least this tier". Each tier generates only its own capability. Advancing every residence therefore destroys the capability that primary production needs. The lowest tier remains structurally necessary, not merely historically present. This single rule turns tier progression into an optimization problem instead of a one-way street. The framework enforces it through exact capability matching (Section 14); substitution between capabilities exists only if explicitly configured.

### 3.5 Breadth versus depth

Needs are satisfied per **category**, not per mandatory individual resource. Members of a category carry value weights, and higher-complexity resources carry higher weights. The same category fulfillment can be reached either through **breadth** (many simple resources) or **depth** (few complex, high-value resources), at entirely different costs in space, workforce, and logistics. This is the central recurring player decision and the reason weighted category evaluation is a framework invariant.

### 3.6 Two decision geometries: flow and coverage

Most needs are satisfied by **resource flow**, which rewards broad specialization and spreads production across locations. At least one need type is satisfied by **spatial coverage** (a provider covering residences within a configured relation such as a radius) and consumes no resources. Coverage rewards compact settlement geometry. The tension between flow-driven sprawl and coverage-driven compactness is a core mechanic, not ornamentation.

### 3.7 Self-correcting failure instead of defeat

The core simulation never ends and has no defeat state. Failure is a deterministic, recoverable **loss spiral**:

```text
Negative balance → entities forcibly paused → supply gap → need fulfillment falls
 → decline transitions → population outputs (income, workforce) fall → ...
```

The player recovers by rebalancing. The pressure to secure supply **before** growth comes from the asymmetry between advancement (paid, gradual) and decline (unrefunded, with population loss).

### 3.8 The planning currency: supported population

Per-capita demand is explicit configuration data. Therefore every production chain can be expressed as **"population of tier X supported"**. This derived figure is the genre's actual planning currency. The framework must make it computable for every resource flow, and clients must be able to show it (Presentation Integration Contract, planning read model).

### 3.9 Abstraction over micromanagement

There is at most one class of controllable unit: the transport unit between locations. Everything else is aggregated. Internal goods movement inside a location is a number (throughput capacity), not objects. Population is an aggregate, not individuals. Logistics remains limited and expandable without micromanagement.

### 3.10 Legible ratios

Rates are constant and integer-divisible so that chain ratios resolve cleanly (for example 2 extractors : 2 refiners : 1 extractor : 1 combiner). Planning must be possible by arithmetic, not by trial and error. The framework supports this through fixed-point integer rates and deterministic per-tick division; content should choose rates accordingly.

### 3.11 Trade buffers, it never replaces production

External exchanges exist without opponents. They provide starting capital and a buffer against shortages. Mandatory price elasticity guarantees that trade can never become a money-generating exploit or a substitute for domestic production chains (Section 17).

## 4. Framework Invariants

### 4.1 Population is tiered

Population exists as aggregate quantities in residence entities. Every population group belongs to exactly one tier definition.

A tier may define:

- Residence capacity
- Need categories and needs
- Population-generated resources or capabilities
- Consumption modifiers
- Growth rules
- Advancement transitions
- Decline transitions

Tier graphs may be linear, branching, parallel, region-specific, or intentionally cyclical when explicitly enabled. The framework assigns no semantic meaning to any tier.

### 4.2 Needs are categorized

A need represents configurable demand. Need categories aggregate individual needs and may require:

- All members
- Any member
- A fixed count
- A weighted score
- A minimum average
- A minimum member fulfillment

Needs may be fulfilled through resource consumption, resource availability, service capacity, spatial coverage, or queryable state. Category requirements may differ per population tier, so higher tiers can demand more of the same category.

### 4.3 Production is resource transformation

A production process:

1. Checks conditions
2. Reserves inputs and output capacity
3. Requires configured capabilities
4. Advances for a configured duration
5. Commits input consumption
6. Produces configured outputs

A process starts only when its **complete** input set and its **complete** capability requirement are available; otherwise it stays idle with a machine-readable block reason. Idleness does not suspend maintenance unless configured.

There are no hard-coded raw, intermediate, consumer, or construction resource classes. Such roles are tags and references.

### 4.4 Resource availability is spatial

The world consists of locations with independent properties, sources, capacity, entities, and inventories. Resource sources may be constrained by deposits, tags, surfaces, region membership, slots, location property values, or area availability.

No location is required to be self-sufficient. Configurations intended as complete games should make self-sufficiency impossible (Section 3.3).

### 4.5 Inventories are isolated

Resources produced at one location are unavailable at another unless moved through a configured transport process. This is the core logistics invariant.

### 4.6 Progression is state-driven

Progression is expressed through conditions evaluated against simulation state, such as population, needs, resources, entities, capabilities, locations, and unlocks. Population thresholds replace research: the framework includes no predefined research tree or campaign.

### 4.7 Capability requirements are exact

A capability requirement is satisfied only by the referenced capability resource. There is no implicit ordering, hierarchy, or "at least this tier" substitution between capabilities. Substitution exists only when explicitly configured.

### 4.8 Continuous costs are independent of utilization

Maintenance is charged per configured interval while an entity exists in a charging state, regardless of whether it is producing. An idle producer is a pure loss. Chain balancing is therefore an economic necessity, not merely an optimization.

### 4.9 The simulation never ends by itself

The core simulation has no defeat or victory state. Shortages, deficits, and decline are recoverable state, resolved through deterministic policies. Ending conditions exist only in the optional scenario module.

## 6. World and Location Model

### 6.1 Location

A location is the smallest independently inventoried spatial domain. It requires:

- Stable identifier
- Spatial-policy reference
- Capacity or topology
- Property tags
- Region membership
- Property vector (named numeric properties, e.g. per-resource suitability)
- Resource source definitions or instances
- Inventory references
- Internal-logistics policy and throughput
- Entity membership
- Connection endpoints
- Activation and establishment state
- Optional owner

The framework must support at least:

- Grid-based spatial locations, including a configurable fraction of non-buildable cells
- Abstract capacity-based locations

The economic simulation must depend only on a spatial-policy interface, not on a specific geometry.

There are no construction links between locations. Entities belong to exactly one location; locations interact only through connections.

### 6.2 Location activation

An inactive location retains state but does not run configurable processes except those explicitly marked as active while suspended. Activation can be initial, command-driven, condition-driven, or the result of establishment (Section 16.3).

### 6.3 Location connection

A connection defines potential transport between two locations:

- Origin and destination
- Directionality
- Base traversal duration (at reference speed; a unit's speed scales it)
- Traversal cost
- Allowed transport tags
- Optional resource restrictions
- Enabled state

A connection does not move resources by itself. Connections are usable only by transport processes; they never extend placement, coverage, or inventory access.

### 6.4 Regions and distribution rules

A region is a named group of locations. Every location belongs to exactly one region when regions are configured.

Regions exist to express **distribution rules**: which resources and source types can occur in which locations. A distribution rule may declare that the source sets or property vectors of two regions are **disjoint**, so that no location and no region can supply every raw resource. This rule, not geography, is the reason long-distance logistics exists (Section 3.3).

Regions may also scope exchanges, unlocks, tier graphs, and conditions.

### 6.5 Location property vector

A location carries a vector of named numeric properties defined by content. A typical use is **suitability**: one value per area-extractable resource (for example 0%, 50%, or 100%) that linearly scales the output of area-dependent sources. Property values are referenced by sources, conditions, placement predicates, and modifiers; the framework assigns them no meaning.

### 6.6 Internal logistics throughput

Each location may define an internal-logistics throughput: the maximum resource quantity per tick that may move between entities and the location inventory. Throughput is a location-scoped capability that storage or hub entities can increase. Its allocation is defined in Section 15.1.

## 7. Resource Model

### 7.1 Resource definition

A resource is immutable content data identified by a stable ID.

```yaml
resource:
  id: example.resource.a
  tags:
    - category.primary
    - storable
  quantity:
    precision: fixed
    scale: 1000
  storage:
    default_policy: shared
  transportable: true
  presentation_key: example.resource.a
```

The simulation resource definition must not contain display names, icons, models, sounds, or descriptive text.

### 7.2 Resource roles

Roles are tags only. Behavior arises from explicit references by systems. A resource is consumed by population because a need references it, not because it has a consumer-goods tag.

Resource roles are distinguished by **function**, never by fiction. A typical complete configuration uses the following functional roles, all expressed through references:

| Functional role | Origin (configured by) | Sink (configured by) |
| --- | --- | --- |
| Primary | Resource sources only | Recipes |
| Intermediate | Recipe with one input | Further recipes |
| Consumer | Recipe with several inputs | Need consumption (destroyed) |
| Construction | Dedicated recipe branches | One-time construction and transition costs |
| Establishment | Expensive recipe | Establishing a new location (Section 16.3) |

A resource may also carry a **complexity** value used as a need-category weight (Section 12.3). Complexity is content data, not a framework class.

### 7.3 Virtual resources and capabilities

Non-storable values use the same definition registry but a recomputed or scoped storage policy.

```yaml
resource:
  id: example.capability.tier_1
  tags: [virtual, capability]
  storage:
    policy: recomputed
    scope: location
  transportable: false
```

Capabilities may represent labor, processing capacity, energy, service capacity, internal-logistics throughput, or any configured operating constraint. None is hard-coded. Labor-type capabilities are typically location-scoped and non-transportable: workforce must live where it works.

### 7.4 Scope

A resource may be scoped to:

- Entity
- Location
- Connected-location group
- Region
- Owner/player
- Global simulation

### 7.5 Balance resources

An owner- or global-scoped accounting resource (for example a currency) may declare `allow_negative: true`. Only such balance resources may fall below zero; every other stored quantity must remain non-negative. A negative balance is not a defeat condition. It triggers the owner deficit policy (Section 20.3).

## 8. Inventory Model

### 8.1 Inventory structure

An inventory stores:

- Resource quantities
- Capacity rules (total, per resource type, or both)
- Acceptance rules
- Reservation ledger
- Access policy
- Purpose locks
- Ownership scope
- Revision counter

Inventories may belong to locations, entities, transport units, or endpoints.

Capacity may be expanded by storage-provider entities (Section 9.7). A capacity rule of the form "N per resource type" is a first-class option.

### 8.2 Inventory policies

Supported policies include:

- Shared
- Private
- Input-only
- Output-only
- Transport cargo
- Infinite source
- Sink
- Recomputed virtual store

Policies are composable where validation allows it.

### 8.3 Reservations

All future consumption uses atomic reservations.

```text
Requested → Granted → Committed
                    ↘ Released
```

Rules:

- Reserved quantity remains stored but unavailable to other consumers.
- A reservation has an owner, purpose, expiry policy, and quantity.
- Commit removes the reserved quantity.
- Release restores availability.
- Total reservations may never exceed stored quantity.

### 8.4 Capacity reservation

Processes that create outputs may reserve destination capacity before starting. Configuration chooses whether output-capacity reservation is mandatory, optional, or disabled.

### 8.5 Purpose locks

Every inventory access carries a **purpose** (for example `production_input`, `population_need`, `construction`, `population_transition`, `transport_load`, `exchange_sale`). An owner may lock an individual resource in an inventory against one or more purposes. Locked quantities remain stored and available for all other purposes.

The canonical use is the **pacing brake**: locking construction resources against `population_transition` stops residences from consuming them for advancement. Without it, a settlement can grow faster than its supply and tip into a decline spiral. Purpose locks are set by command and are authoritative state.

## 9. Entity and Building Framework

A building is an entity assembled from components, not a class in an inheritance hierarchy.

### 9.1 Generic lifecycle

```text
Planned → Awaiting resources → Constructing → Active
                                      │         │
                                      │         ├→ Disabled
                                      │         └→ Blocked
                                      └→ Cancelled
Active/Disabled/Blocked → Deconstructed
```

Lifecycle states are generic. Presentation labels are external.

### 9.2 Composable capabilities

The framework supplies data components for:

- Construction and deconstruction
- Placement
- Residence
- Producer
- Resource source
- Storage provider
- Transport endpoint
- Service provider
- Capability provider
- Capability consumer
- Maintenance consumer
- Connectivity provider and requirement
- Modifier source and receiver
- Location hub
- Exchange

Economically, any building is fully described by the tuple **(input vector, output rate, footprint, capability demand, maintenance)**. Every additional building name in a configured game is a parameterization of a small set of archetypes (Section 9.11).

### 9.3 Residence

A residence component contains:

- Supported population tier
- Current population
- Capacity
- Need-state references
- Growth-policy reference
- Transition-state reference
- Empty-residence policy

The empty-residence policy defines what happens when population reaches zero through decline: retain the empty residence, revert it to a configured definition, or decay (deconstruct) it after a configured delay.

### 9.4 Producer

A producer component contains:

- Available recipe handles
- Selected recipe
- Concurrent process slots
- Input/output inventory references
- Process states
- Modifier collection

### 9.5 Resource source

Supported source policies:

- Infinite rate
- Finite deposit
- Regenerating deposit
- Area-dependent extraction
- Slot-dependent extraction
- Condition-dependent generation

**Slot-dependent extraction** binds exactly one extractor to one source slot of a matching type. A location has a finite number of slots (possibly zero) per source type. A slot may have unlimited operating life; scarcity then lies in the number of slots, not in depletion.

**Area-dependent extraction** requires a configured exclusive working area in addition to the footprint. Its output is multiplied by a referenced location property value (for example suitability 0%, 50%, 100%), linearly and deterministically.

### 9.6 Service provider

A service provider generates configured capacity or coverage. It does not assign meaning to the service.

A **coverage** provider covers every residence within a configured spatial relation (for example a radius in cells) and may consume no resources at all. It is the only mechanism by which a need is satisfied through geometry instead of flow (Section 3.6).

### 9.7 Storage provider

A storage provider creates or modifies inventory capacity and access. It may also increase the location's internal-logistics throughput.

### 9.8 Transport endpoint

A transport endpoint defines loading, unloading, throughput, compatibility, and inventory access. An endpoint may berth transport units.

### 9.9 Location hub

A location hub is the root entity of an established location. Typically it:

- Owns the location's shared inventory and its base capacity
- Provides the base internal-logistics throughput
- Is the connectivity root that other entities must connect to
- Is the transport endpoint and berth of the location
- Is the interface to exchanges

A location may be configured to have no hub; then these responsibilities are assigned to other entities or to the location itself.

### 9.10 Exchange

An exchange component turns an entity or a fixed world node into a trading counterparty. See Section 17.

### 9.11 Archetypes

A small set of archetypes covers a complete game. They are composition patterns, not framework classes:

| Archetype | Principal components | Decision it creates |
| --- | --- | --- |
| Location hub | Location hub, storage provider, transport endpoint, maintenance | Where to expand |
| Connector | Connectivity provider, maintenance | Layout and binary connectivity |
| Slot extractor | Resource source (slot), capability consumer, maintenance | Use of finite slots |
| Area extractor | Resource source (area × property), capability consumer, maintenance | Where suitability is high enough |
| Refiner | Producer (1 input), capability consumer, maintenance | Chain ratios |
| Combiner | Producer (2–3 inputs), capability consumer, maintenance | Chain composition, cross-location inputs |
| Advanced combiner | Producer with at least one input from another region | Cross-region dependency |
| Residence | Residence, transitions | Population, capabilities, income |
| Coverage service | Service provider (coverage), capability consumer, maintenance | Compact geometry |
| Storage module | Storage provider (capacity + throughput), maintenance | Buffer and throughput expansion |

## 10. Production Model

### 10.1 Recipe definition

```yaml
recipe:
  id: example.recipe.c
  duration_ticks: 60
  inputs:
    - resource: example.resource.a
      quantity: 2000
    - resource: example.resource.b
      quantity: 1000
  outputs:
    - resource: example.resource.c
      quantity: 1000
  capability_requirements:
    - resource: example.capability.tier_1
      quantity: 10
  conditions:
    all:
      - type: location_has_tag
        tag: example.property.x
```

Quantities above are fixed-point base units.

### 10.2 Production state machine

```text
Idle
 → Validate entity and recipe conditions
 → Reserve capabilities when required
 → Reserve inputs
 → Reserve output capacity
 → Processing
 → Commit inputs
 → Deposit outputs
 → Release reservations
 → Idle
```

A process is **all-or-nothing**: it starts only when every input and every capability requirement can be reserved in full. Partial starts do not exist. While idle or blocked, the entity keeps paying maintenance unless its maintenance policy says otherwise (Section 20).

Within a location, entity-to-inventory access is **binary**: an entity either satisfies the location's connectivity requirement (for example a connector path to the hub) or it has no inventory access. Distance inside a location does not change rates.

### 10.3 Blocking

A process exposes one or more machine-readable block reasons:

- Entity disabled
- Paused by owner deficit policy
- Invalid recipe
- Condition false
- Missing input
- Missing capability
- Missing inventory access
- Missing output capacity
- Throughput throttled (partial rate)
- Location inactive

The presentation layer can represent these but cannot calculate them.

### 10.4 Batch and continuous processes

A batch process commits at completion. A continuous process divides rates deterministically per tick. Both use the same inputs, outputs, conditions, and capability definitions.

Rates are constant. Content should choose integer-divisible rates so chain ratios resolve to whole entity counts (Section 3.10).

### 10.5 Productivity modifiers

Modifiers may affect:

- Duration
- Input quantity
- Output quantity
- Capability requirement
- Maintenance requirement

Modifier order is fixed by architecture:

1. Base definition
2. Definition-local modifiers
3. Entity modifiers
4. Location modifiers
5. Owner/global modifiers
6. Clamps and rounding

Modifiers only scale existing rates. Systems such as items, specialists, or equipment are therefore not framework concepts: if a configuration wants them, they reduce to modifier sources and must not introduce new mechanics.

### 10.6 Chain metrics

Because recipe rates and per-capita need demand are both configuration data, the framework must be able to derive, for any resource flow:

- Net production and consumption rate per location and per owner
- Capability, footprint, and maintenance cost of the chain
- **Supported population**: `net rate ÷ (per-capita demand × tier consumption factor)` for every tier that consumes the resource

Supported population is the primary planning figure (Section 3.8). It is a derived read-model value, never authoritative state.

## 11. Population Model

### 11.1 Aggregate population

Individual inhabitants are not authoritative simulation entities. Population groups are aggregate quantities associated with residence entities or locations.

A population group contains:

- Tier handle
- Current count
- Capacity
- Need states
- Growth progress
- Generated outputs
- Transition progress

### 11.2 Population-tier definition

```yaml
population_tier:
  id: example.population.tier_1
  residence_capacity:
    base: 10
  consumption_factor: 1000
  need_categories:
    - example.need_category.a
  outputs:
    - resource: example.capability.tier_1
      rate_per_population_per_tick: 1000
      scope: location
    - resource: example.resource.currency
      rate_per_population_per_tick: 100
      scope: owner
      satisfaction_curve: example.curve.income_by_satisfaction
  growth_policy: example.growth.default
  advancement_transitions:
    - example.transition.tier_1_to_2
  decline_transitions: []
```

`consumption_factor` (fixed scale, 1000 = 1.0) multiplies the per-capita demand of every resource-consumption need of this tier. Higher tiers typically consume more per inhabitant, have larger residence capacity, and generate more income per inhabitant.

### 11.3 Population outputs

A tier may generate any configured resource or capability. Outputs may depend on:

- Current count
- Occupancy ratio
- Need fulfillment and residence satisfaction
- Residence state
- Modifiers

Income and workforce are not special framework concepts. They are simply the two outputs every complete configuration needs to close the loop: an owner-scoped balance resource and location-scoped, non-transportable capabilities.

**Pyramid rule.** Each tier should output its **own** capability, and producers should require a **specific** capability (Section 4.7). Advancing a residence therefore removes the capability of its source tier from the location. Validation reports configurations in which a higher tier's capability can satisfy a lower tier's requirement, because they disable the pyramid trade-off.

### 11.4 Growth

Growth policies define:

- Evaluation interval
- Conditions
- Increase rate
- Decrease rate
- Capacity behavior
- Minimum population
- Fraction accumulation and rounding

```yaml
population_growth:
  id: example.growth.default
  interval_ticks: 10
  increase:
    amount: 1
    conditions:
      all:
        - type: aggregate_need_fulfillment
          operator: greater_equal
          value: 800
        - type: available_population_capacity
          operator: greater
          value: 0
  decrease:
    amount: 1
    conditions:
      all:
        - type: aggregate_need_fulfillment
          operator: less
          value: 250
```

Fulfillment values use a fixed scale, here 0 to 1000.

Growth is evaluated against the residence satisfaction (Section 12.5). Typical configurations combine growth with satisfaction bands: high satisfaction admits influx until capacity, a middle band is stable, a low band triggers decline after a grace period, and the lowest band causes emigration until the residence is empty.

## 12. Need Framework

### 12.1 Need definition

```yaml
need:
  id: example.need.a1
  category: example.need_category.a
  applies_to:
    population_tiers: [example.population.tier_1]
  demand:
    type: resource_consumption
    resource: example.resource.c
    quantity_per_population_per_tick: 10
  fulfillment:
    measurement_window_ticks: 300
    target_ratio: 1000
  effects:
    - target: population_output
      target_id: example.resource.currency
      curve: example.curve.need_output
```

### 12.2 Supplier types

#### Resource consumption

Consumes resource units from an accessible inventory.

#### Resource availability

Tests availability without consumption.

#### Service capacity

Allocates a generated capability to demand.

#### Spatial coverage

Evaluates whether a residence belongs to a provider’s configured coverage relation. Coverage consumes no resources. A covered residence counts as fully supplied for that need; the category requirement can still demand coverage by several distinct providers or provider types.

#### State query

Evaluates a constrained domain query.

### 12.3 Need category

```yaml
need_category:
  id: example.need_category.a
  evaluation:
    mode: weighted_score
    required_score: 2000
    required_score_by_tier:
      example.population.tier_1: 1000
      example.population.tier_2: 2000
      example.population.tier_3: 3000
  members:
    - need: example.need.a1
      weight: 1000
    - need: example.need.a2
      weight: 2000
```

Supported modes:

- `all`
- `any`
- `count`
- `weighted_score`
- `average`
- `minimum`

`required_score_by_tier` overrides `required_score` for the listed tiers. A category is **active** for a tier when the tier lists it in `need_categories`.

**Weighted-score semantics** (fixed scale, 1000 = 1.0):

```text
a_n  = min(1, delivered_n / demanded_n)              per member need n
S_k  = Σ (weight_n × a_n)                            per category k
D_k  = min(1, S_k / required_score_k(tier))           category fulfillment
```

Member weights should reflect resource complexity (for example complexity 1 → weight 1, complexity 4 → weight 4). Because every member is capped at full supply but contributes its weight, the same `D_k` can be reached by many low-weight members (**breadth**) or by few high-weight members (**depth**). This is the framework's central recurring decision (Section 3.5) and the reason individual resources are never individually mandatory unless content chooses `all`.

### 12.4 Evaluation sequence

```text
Population count
 → raw demand (per-capita demand × count × tier consumption factor)
 → accessible supply or allocated service
 → delivered amount
 → fulfillment ratio over measurement window
 → need-category aggregation
 → residence satisfaction
 → satisfaction bands and configured effects
```

Demand, delivery, fulfillment, category result, satisfaction, and effects must remain separate state values for diagnostics.

### 12.5 Residence satisfaction

Residence satisfaction `Z` aggregates the fulfillment of all categories active for the residence's tier. The aggregation mode is configured per tier or globally:

- `average` (default): arithmetic mean of active `D_k`
- `minimum`: the weakest active category
- `weighted_average`: configured category weights

`aggregate_need_fulfillment` in conditions refers to `Z`.

### 12.6 Satisfaction bands

A satisfaction-band table maps ranges of `Z` to effects. Bands are content data; the framework supplies the effect types:

```yaml
satisfaction_bands:
  id: example.bands.default
  bands:
    - min: 800
      effects:
        - { type: growth, policy: example.growth.influx }
        - { type: output_multiplier, resource: example.resource.currency, value: 1000 }
        - { type: enable_advancement }
    - min: 500
      effects:
        - { type: output_multiplier, resource: example.resource.currency, value: 700 }
    - min: 250
      effects:
        - { type: output_multiplier, resource: example.resource.currency, value: 400 }
        - { type: trigger_decline, transition: example.transition.tier_2_to_1, grace_ticks: 60 }
    - min: 0
      effects:
        - { type: growth, policy: example.growth.emigration }
```

Band changes take effect deterministically at evaluation. A grace period is a sustained-condition timer (Section 13.2): leaving the band before it expires cancels the effect.

`trigger_decline` names the decline transition to start. If `transition` is omitted, the tier's `decline_transitions` must contain exactly one entry; for a tier without decline transitions (typically the lowest) the effect does nothing. Bands may be shared between tiers or defined per tier.

## 13. Tier Transitions

### 13.1 Advancement

```yaml
transition:
  id: example.transition.tier_1_to_2
  source_tier: example.population.tier_1
  target_tier: example.population.tier_2
  trigger: manual_command
  conditions:
    all:
      - type: residence_at_capacity
      - type: sustained
        ticks: 60
        condition:
          type: aggregate_need_fulfillment
          operator: greater_equal
          value: 800
      - type: population_count
        tier: example.population.tier_1
        scope: owner
        operator: greater_equal
        value: 100
  costs:
    - resource: example.resource.construction_a
      quantity: 10000
  cost_source: location_inventory
  cost_access_purpose: population_transition
  duration_ticks: 10
  conversion:
    population: retain_count
    entity_definition: replace
```

The canonical advancement combines four simultaneous conditions:

1. **Occupancy**: the residence is at capacity.
2. **Satisfaction**: `Z` has been at or above a threshold continuously for a configured duration.
3. **Costs**: construction resources are available in the residence's location inventory and not locked for the `population_transition` purpose (Section 8.5). They are consumed immediately at start.
4. **Global unlock**: a cumulative population threshold of the source tier (or another unlock) has been reached.

Costs are always paid from the inventory of the location the residence stands in. Inventory isolation therefore applies to progression as well: advancing a remote location requires shipping construction resources to it.

### 13.2 Transition triggering

Supported trigger modes:

- Manual command
- Automatic when eligible
- Scheduled
- Condition duration

`sustained` is a temporal condition: it holds once its inner condition has been continuously true for the given number of ticks. It is used for advancement thresholds and decline grace periods.

### 13.3 Conversion policies

Population conversion:

- Retain count
- Retain occupancy ratio
- Set fixed count
- Apply multiplier
- Clamp to target capacity (excess population is removed)

Entity conversion:

- Replace definition
- Modify components
- Spawn target and remove source

Cost refund policy:

- None
- Fixed fraction of the source transition's costs
- Configured resource list

### 13.4 Decline

Decline is the same transition mechanism with different conditions and target tier. It can be enabled, disabled, delayed, automatic, or command-driven.

**Asymmetry rule.** In a complete configuration decline should be strictly more expensive than advancement: no refund of construction resources, population clamped to the lower capacity (excess population is lost), and the loss of the higher tier's capability and income. This asymmetry creates the pressure to secure supply **before** growth (Section 3.7).

### 13.5 Initial construction

Constructing a new residence of the lowest tier is an ordinary construction (Section 18) with its own costs. It is the entry point of the tier graph.

## 14. Capability Model

### 14.1 Capability definition

Capabilities use resource definitions with allocation metadata:

- Scope
- Provider rate or quantity
- Consumer quantity
- Allocation model
- Priority
- Shortage behavior
- Optional explicit substitution list

Matching is exact (Section 4.7). A capability resource satisfies only requirements that reference it directly or through an explicit substitution list. Labor-type capabilities are typically location-scoped and non-transportable, so workforce must be housed in the same location where it is used.

### 14.2 Allocation models

#### Binary

A consumer receives its complete request or none.

#### Proportional

All consumers receive a deterministic fraction.

#### Priority sequential

Requests are fulfilled in priority order, then stable entity order.

#### Weighted proportional

Available quantity is divided according to configured weights.

### 14.3 Shortage behavior

A consumer may:

- Stop
- Scale process duration
- Scale output
- Accumulate shortage debt
- Enter a configured state

## 15. Logistics Model

### 15.1 Internal logistics policies

A configuration selects per location or inventory network:

- Shared inventory access
- Throughput-limited shared access
- Connectivity graph access
- Explicit internal transport

All production and need systems use the same inventory-access contract.

**Throughput-limited shared access** is the recommended default for complete games. Internal carriers are not units; internal logistics is a number. Every entity that moves resources between itself and the location inventory (inputs, outputs, need deliveries, transport handling where configured) requests throughput equal to the quantity it moves per tick. If total requested throughput exceeds the location's throughput capacity, all requesters are throttled **proportionally** and deterministically, and the throttled ones report `throughput_throttled`. Throughput is expanded by storage providers or hub upgrades.

This preserves the mechanic that internal logistics is limited and expandable while removing all carrier micromanagement (Section 3.9). Combined with connectivity, it punishes over-densification.

### 15.2 Inter-location transport order

A transport order is a **route**: an ordered station list that a unit executes indefinitely without player intervention.

```yaml
transport_order:
  id: runtime.route.1
  mode: route
  stations:
    - endpoint: 1001
      actions:
        - resource: example.resource.c
          action: load
          rule: { mode: excess_above, quantity: 100000 }
        - resource: example.resource.d
          action: load
          rule: { mode: up_to_capacity }
    - endpoint: 2001
      actions:
        - resource: example.resource.c
          action: unload
          rule: { mode: maintain_destination_target, quantity: 200000 }
    - endpoint: 3001
      actions:
        - resource: example.resource.d
          action: unload
          rule: { mode: all }
  path_policy: shortest_stable
  scheduling:
    repeat: true
    wait_policy: never
```

A simple origin→destination order is a two-station route. Paths between consecutive stations are planned through connections deterministically.

### 15.3 Quantity rules

Supported rules:

- Fixed quantity
- Up to cargo capacity (until full)
- All carried
- Excess above origin reserve (only surplus above threshold)
- Deficit below destination target
- Maintain origin minimum
- Maintain destination target
- Priority list

Loading respects purpose locks (`transport_load`) and reservations.

### 15.4 Transport units

```yaml
transport_unit:
  id: example.transport.basic
  cargo:
    compartment_policy: typed_slots
    slots: 2
    slot_capacity: 50000
  movement:
    allowed_connection_tags: [example.connection.standard]
    speed_permille: 1000
  handling:
    loading_rate_per_tick: 10000
    unloading_rate_per_tick: 10000
  maintenance:
    costs:
      - resource: example.resource.currency
        quantity_per_tick: 100
```

Compartment policies:

- `unrestricted`: one shared capacity for any resource mix
- `typed_slots`: a fixed number of slots; each slot holds exactly one resource type at a time
- `per_resource`: fixed capacity per listed resource

Transport units are built like other entities (construction costs) and pay maintenance continuously. Configurations typically offer a few unit classes that trade capacity against speed and cost.

Configuration may represent transport as physical units, scheduled abstract capacity, or delayed transfers. The observable domain contract must stay consistent.

The transport unit is the only controllable unit class the framework defines. All other movement is aggregated (Section 3.9).

### 15.5 Transport order modes

| Mode | Behavior |
| --- | --- |
| `route` | Executes the station list repeatedly (Section 15.2). |
| `explore` | Travels to a target location and reveals its attributes to the owner (Section 16.1). |
| `establish` | Carries the establishment cost to an unoccupied location and establishes it (Section 16.3). |
| `trade` | Buys or sells at an exchange within price and quantity limits (Section 17). |

Trade actions may also be stations inside a `route`, so a standing route can sell surplus or buy shortfalls automatically.

### 15.6 Transport lifecycle

```text
Unassigned
 → Assigned to order
 → Moving to next station or target
 → Loading / Unloading / Trading / Exploring / Establishing
 → Next station, repeat, or Unassigned
```

### 15.7 Failure behavior

All transport failure handling is explicit:

- Origin unavailable
- Destination unavailable
- Connection unavailable
- Resource unavailable
- Cargo cannot unload
- Unit disabled
- Exchange price or quantity limit not met
- Establishment target already occupied

Each order defines skip, wait, retry, return, or fail behavior.

## 16. Exploration and Location Establishment

### 16.1 Knowledge state (fog)

Each owner has a knowledge state per location: `unknown`, `discovered`, or `established`. The attributes of an unknown location (property vector, source slots, region membership, capacity) exist authoritatively but are **not visible** to that owner. They become visible when a transport unit of the owner visits the location (`explore` mode, or any traversal that ends there), or when a configured condition reveals them.

Knowledge state is authoritative, per owner, deterministic, and saved. Read models filter location attributes by the requesting owner's knowledge state (Presentation Integration Contract). Fog may be disabled per configuration.

### 16.2 Why exploration exists

Exploration turns expansion into a decision under incomplete information: a location's suitability and slots are worth knowing before an expensive establishment cost is spent there. It feeds directly into the spatial-scarcity and logistics layers and is therefore not decoration.

### 16.3 Establishment (founding a location)

A location becomes usable for an owner through **establishment**:

```yaml
location_establishment:
  id: example.establishment.default
  requires_knowledge: discovered
  requires_unoccupied: true
  cost_source: transport_cargo
  costs:
    - resource: example.resource.establishment_package
      quantity: 1000
  creates_hub: example.entity.hub
  activation: on_completion
  ownership: exclusive
```

Rules:

- Establishment costs are paid from the cargo of an arriving transport unit (`establish` mode), not from a remote inventory. Inventory isolation therefore applies to expansion as well.
- Completion creates the configured hub entity and the location inventory, and activates the location for the owner.
- With `ownership: exclusive`, an established location cannot be established by another owner.
- The initial location(s) of an owner are established by scenario setup.

A configuration may also allow establishment through a construction plan or a condition; the transport-cargo variant is the reference behavior.

## 17. Exchanges (Trade Without Opponents)

### 17.1 Purpose

An exchange is a fixed trading counterparty that buys and sells resources against an owner-scoped balance resource. It requires no opponent. Trade is a **buffer and a source of starting capital, never a replacement for domestic production** (Section 3.11).

### 17.2 Exchange definition

```yaml
exchange:
  id: example.exchange.region_a
  location: example.location.trade_node_a
  currency: example.resource.currency
  goods:
    - resource: example.resource.c
      buy_from_exchange: { base_price: 12000, enabled: true }
      sell_to_exchange:  { base_price: 8000,  enabled: true }
  elasticity:
    window_ticks: 600
    step_quantity: 100000
    step_change_permille: 20
    recovery_permille_per_interval: 50
    recovery_interval_ticks: 60
    min_price_permille: 100
    max_price_permille: 5000
  shared_between_owners: true
```

An exchange can be a world node (a location without production) or an entity. Typically there is one exchange per region. Exchanges are reached by transport units through connections, like any other endpoint.

### 17.3 Mandatory price elasticity

Without elasticity, any price spread between production cost and sale price is an unbounded money exploit. Elasticity is therefore mandatory; an exchange without it fails validation.

- Selling a resource lowers its sale price by `step_change_permille` for every `step_quantity` sold within `window_ticks`.
- Buying a resource raises its purchase price by the same rule.
- Prices recover toward the base price by `recovery_permille_per_interval` per `recovery_interval_ticks`.
- Prices are clamped to configured bounds.
- All price arithmetic is fixed-point and deterministic. Price state is authoritative and saved.

Validation also rejects exchanges where an immediate buy-then-sell of the same resource can be profitable, and warns when a recipe's outputs can be sold above the purchase cost of its inputs at base prices with no elasticity limit reached.

### 17.4 Trade execution

A trade action specifies resource, direction, quantity rule, and a price limit (minimum sale price or maximum purchase price). Execution is atomic per action: the cargo transfer and the balance transaction commit together or not at all. Trades are ordered deterministically by tick, exchange, owner, and transport-unit ID.

With multiple owners, a shared exchange aggregates all owners' volume into the same elasticity state. Competition is thereby expressed purely as price pressure (Section 21).

## 20. Continuous Economy and Deficit Resolution

### 20.1 Maintenance

Continuous costs and outputs are deterministic periodic transactions.

```yaml
maintenance:
  interval_ticks: 60
  inputs:
    - resource: example.resource.currency
      quantity: 5000
  charge_policy: while_enabled
  shortage_policy: owner_deficit_policy
```

Charge policies:

- `while_exists`: from construction completion until deconstruction
- `while_enabled` (reference): whenever not disabled or paused, **regardless of utilization**
- `while_active`: only while not blocked
- `while_processing`: only while a process advances

The reference policy charges idle and blocked entities. An idle producer is a pure loss, so balancing chains is an economic necessity (Section 4.8).

Supported shortage policies:

- Deactivate entity
- Scale
- Accumulate debt resource
- Ignore
- Trigger transition
- Delegate to the owner deficit policy

### 20.2 Owner balance model

For an owner-scoped balance resource the framework derives, every tick:

```text
Revenue/interval  = Σ population outputs of that resource (after satisfaction multipliers)
                  + exchange sales
Expenses/interval = Σ entity maintenance + Σ transport-unit maintenance
                  + exchange purchases
```

These are read-model values. The authoritative balance changes only through transactions.

### 20.3 Owner deficit policy

Instead of bankruptcy or defeat, a deficit triggers a deterministic correction:

```yaml
deficit_policy:
  id: example.deficit.default
  resource: example.resource.currency
  trigger: { operator: less, value: 0 }
  action: pause_entities
  order: [maintenance_desc, entity_id_asc]
  stop_when: net_rate_non_negative
  exclude_tags: [example.tag.hub]
  resume:
    policy: automatic_reverse_order
    when: { operator: greater_equal, value: 0 }
```

Rules:

- When the trigger holds, entities are paused one by one in the configured order (reference: **highest maintenance first**, then stable entity ID) until the stop condition holds.
- Paused entities report `paused_by_deficit`, pay no maintenance, and are distinct from player-disabled entities.
- Resume is automatic in reverse order, manual by command, or disabled.
- The resulting chain (pause → supply gap → need fulfillment falls → decline → income falls) is the core loss spiral. It replaces every external threat (Section 3.7).

There is no framework-level bankruptcy, defeat, or currency assumption. A configuration without a balance resource is mechanically valid as a test fixture, but it is not a complete game, because the balance currency (Section 2) is missing.

## 21. Optional Modules

Optional modules sit outside the core. The governing rule is: **a module may only use existing core mechanisms and must not feed new mechanics back into the core.** The core must be complete and playable with every module disabled. All modules are disabled by default.

| Module | Minimal rule | Core mechanisms used |
| --- | --- | --- |
| **Other owners** | Additional owners establish locations exclusively and trade at the same shared exchanges, intensifying price elasticity. No other interaction: no shared inventories, no access to foreign locations, no combat, no diplomacy. | Owners, exclusive establishment, shared exchange elasticity |
| **Scenario objective** | Converts the endless simulation into a scenario, e.g. "maintain N population of tier X for T ticks while keeping a non-negative balance". On success or failure the module emits a scenario-result event; whether the session then stops is a session setting, not a mechanic. | Conditions, `sustained` timer, domain events |
| **Disruptions** | A seeded, deterministic stream occasionally disables an eligible entity for a configured duration. Increases the value of redundancy. | Seeded random stream, standard entity disable |

Modules are configuration packages with their own schemas. Replays include their seeds and settings.

## 23. Minimal Valid Configurations

### 23.1 Basic economic loop

A mechanically valid package defines:

1. One active location
2. One accessible inventory
3. One population tier
4. One residence
5. One need
6. One resource satisfying the need
7. One source or recipe path for that resource
8. One mechanism preventing immediate deadlock

### 23.2 Logistics loop

Additionally define:

1. Two isolated locations
2. A necessary resource available at only one
3. A connection
4. Compatible endpoints
5. A transport unit or capacity
6. A transport order

### 23.3 Progression loop

Additionally define:

1. At least two tiers
2. A transition
3. Need-driven eligibility
4. New resources, recipes, capabilities, or constraints associated with the target tier

### 23.4 Complete game loop

A configuration intended as a complete game additionally defines:

1. At least two regions with disjoint raw-resource distribution
2. Slot-limited and area-dependent sources with location property values
3. Tier-specific capabilities with exact matching (pyramid rule)
4. Weighted need categories with tier-specific requirements, including at least one coverage-based need
5. Satisfaction bands with growth, stability, decline with grace period, and emigration
6. A balance resource, utilization-independent maintenance, and an owner deficit policy
7. Throughput-limited internal logistics
8. Purpose locks for transition costs
9. Asymmetric decline (no refund, population clamp)
10. Exploration and establishment of new locations
11. At least one exchange with price elasticity
12. Population-threshold unlocks

### 23.5 Minimum playable prototype

The smallest configuration that contains all five layers in complete and testable form is structural, not numeric:

1. Enough locations in at least two regions that the disjoint distribution rule forces inter-region transport, with more locations than the player can establish at once
2. Enough primary resources that each region lacks at least one
3. At least one intermediate stage, so chains have more than one step
4. Enough consumer resources that at least one weighted category offers a breadth-versus-depth choice
5. Construction resources for building and for advancement
6. Two population tiers, each with its own capability
7. One transport unit class

## 25. Design Acceptance Criteria

The framework is design-complete when:

- A configured population creates visible and traceable demand.
- Every delivered resource has a source, path, and sink.
- Higher tiers can require more complex chains without engine changes.
- A required resource can be isolated spatially and restored through transport configuration.
- A configuration can make every location and every region non-self-sufficient by a distribution rule.
- Lower tiers can remain necessary through exact capability matching (pyramid rule).
- The same category fulfillment can be reached through breadth or depth.
- At least one need can be satisfied by coverage geometry instead of resource flow.
- Idle entities can be configured to keep paying maintenance.
- A deficit resolves through a deterministic, recoverable loss spiral instead of a defeat state.
- Decline can be made strictly more expensive than advancement.
- Advancement can be paced by purpose locks on construction resources.
- Internal logistics can be limited by throughput without carrier entities.
- Unknown locations can be explored and established using transported resources.
- Exchanges provide trade without opponents and cannot be exploited for unbounded income.
- Supported population per chain is derivable for every consumed resource.
- All seven scarcities of Section 3.2 can be active at once, and each can be traced to configuration.
- Advancement and decline use the generic transition engine.
- All concrete terminology can be replaced without changing simulation code.
- The same configuration runs headlessly and through multiple presentation clients.
- A new complete gameplay definition can be created without engine source changes.

---

## 26. Canonical Framework Summary

> A deterministic, headless simulation of aggregate, tiered population groups that create categorized demand and supply the capabilities and income that production requires; configurable entities transform resources through recipes; independently inventoried locations with scarce, disjointly distributed sources constrain resource availability; configurable transport processes connect those inventories; and condition-driven transitions create progression. All tension arises from economic scarcity, not conflict. All concrete content and representation are external data.

### B.3 Archetype parameters

| Archetype | Footprint | Input → Output | Capability | Maintenance/min | Unlock |
| --- | --- | --- | --- | --- | --- |
| Hub (depot) | 4×4; 500 per resource; 60 t/min | – | – | 20 | 1 EP via transport |

| Combiner | 4×4 | 2–3 inputs → 2 C/min | 25 AK2 | 30 | 150 S1 population |

| Coverage service | 4×4, radius 18 | – | 15 AK2 | 45 | 150 S1 population |
| Storage module | 2×2; +300 per resource; +20 t/min | – | 5 AK1 | 10 | Start |

Reference chain: 2 area extractors (P1) → 2 refiners (H1) + 1 slot extractor (P2) → 1 combiner = 2 C1/min. Derived from the archetype table above, it occupies 61 cells of footprint (85 including the two exclusive working areas) and requires **70 AK1 + 25 AK2** — the combiner needs the second tier's capability, which is exactly the pyramid rule at work. At a per-capita demand of `0.01 × f(t)` per minute the chain supports 200 S1 or 133 S2 population.

### B.6 Satisfaction bands

| Z | Effects |
| --- | --- |
| ≥ 0.80 | +1 population every 8 s until capacity; advancement enabled; income ×1.0 |
| 0.50–0.79 | Stable; income ×0.7 |
| 0.25–0.49 | Decline by one tier after 60 s grace; income ×0.4 |
| < 0.25 | −1 population every 4 s; residence decays at zero |
